## Goal

Sustituir el servidor OpenSwoole por Workerman. Un único `Worker` con protocolo HTTP+WebSocket multiplexado en el mismo puerto. En el handshake WebSocket se valida JWT (`?token=` o `Authorization: Bearer`) con `AuthService::authenticateFromToken`; el user_id se asocia a la conexión. Mensajes inválidos cierran la conexión individualmente. Timer de heartbeat hace ping y barre las conexiones muertas. Endpoints HTTP internos `/internal/push|status|auth` (Bearer app_secret) para el cross-process.

## Detalles del upgrade WebSocket manual

El protocolo HTTP de Workerman lee la request y, si el cliente envía los headers correctos, responde con `HTTP/1.1 101 Switching Protocols` y un `Sec-WebSocket-Accept` calculado como `base64(sha1($key . "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))`. Tras enviar la respuesta 101, la conexión pasa a estar en modo "websocket" gestionado por el handshake manual. A partir de ahí, los frames se leen con el parser de WebSocket (más complejo). 

**Decisión pragmática para v1:** usar el protocolo nativo de Workerman `Workerman\Protocols\Websocket` para la parte WS, y enrutar HTTP por prefijo. La forma limpia es: el `Worker` con protocolo `Http` rechaza el `Sec-WebSocket-Key` upgrade (no se puede combinar HTTP+WS en un mismo Worker con protocolo Http de forma nativa). Entonces:
- **Plan B (más simple y robusto):** escuchar HTTP y WebSocket en el **mismo puerto** no es soportado por Workerman; usar **dos Workers** en el mismo archivo (HTTP+WS) sólo funciona en Linux (no Windows). 
- **Plan C (elegido):** HTTP interno en un **puerto separado** (`WEBSOCKET_INTERNAL_PORT`, default 8081, bind `127.0.0.1`). El servidor principal expone sólo el Worker WebSocket en `WEBSOCKET_PORT`. En Windows, un archivo = un Worker = perfecto (no choca con la limitación de "multi workers in one file" porque cada proceso `realtime:start` arranca sólo el WS, y el HTTP interno es otro proceso). En Linux, ambos Workers en el mismo archivo funcionan sin problemas.

Reescribo el paso 2 con Plan C:
- `Worker('websocket://0.0.0.0:8080')` para el WS.
- `Worker('http://127.0.0.1:8081')` para el HTTP interno.
- En Windows: `realtime:start` arranca el WS; un segundo comando (o auto-spawn desde `realtime:start`) levanta el HTTP. **Para no complicar UX, en Windows `realtime:start` levanta WS y HTTP como **procesos separados** vía `proc_open`** (mismo binario PHP, distinto archivo `websocket/internal_http_server.php`).

Esto es más realista. Reescribo el paso 2 con este Plan C y creo `websocket/internal_http_server.php` en WS-03 (HTTP interno aislado). El handshake WS en el puerto 8080 sí usa el protocolo `Websocket` nativo de Workerman (con `onWebSocketConnect` para JWT), que es el patrón soportado.
